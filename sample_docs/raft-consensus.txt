Understanding the Raft Consensus Algorithm

These notes were written for the DocuChat sample corpus as a plain-language summary of the Raft algorithm described by Diego Ongaro and John Ousterhout in 2014.

Why consensus is needed

A replicated state machine keeps several servers in agreement on the same sequence of commands, so the service keeps working when some servers crash. Consensus algorithms make sure every server applies the same commands in the same order. Raft was designed to be easier to understand than Paxos, which had a reputation for being very difficult to teach and implement correctly.

A Raft cluster typically has five servers, which tolerates the failure of two of them. In general, a cluster of 2f + 1 servers survives f failures because any decision needs agreement from a majority, called a quorum.

Server roles and terms

At any time each server is in one of three states: leader, follower or candidate. In normal operation there is exactly one leader and every other server is a follower. Followers are passive: they only respond to requests from leaders and candidates. Clients send all requests to the leader; a follower that receives a client request redirects it to the leader.

Time is divided into terms numbered with consecutive integers. Each term begins with an election. Terms act as a logical clock: every message carries the sender's current term, and a server that sees a higher term immediately updates its own term and reverts to follower. A request carrying a stale term is rejected.

Leader election

The leader sends periodic heartbeats, which are AppendEntries messages with no log entries, to keep its authority. If a follower receives no communication for a period called the election timeout, it assumes there is no viable leader, increments its term, becomes a candidate, votes for itself and sends RequestVote messages to every other server.

A candidate wins if it collects votes from a majority of servers in the same term. Each server votes for at most one candidate per term, on a first-come, first-served basis, which guarantees at most one leader per term.

If many followers become candidates at the same moment, votes can be split so that no one wins. Raft makes split votes rare by choosing each election timeout randomly, for example between 150 and 300 milliseconds, so that usually a single server times out first and wins before the others wake up.

Log replication

Once elected, the leader appends each client command to its log as a new entry and sends AppendEntries messages to the followers in parallel. Each entry stores the command and the term in which the leader received it.

An entry is committed once the leader has replicated it on a majority of servers. The leader then applies the entry to its state machine and returns the result to the client. Followers learn the commit index from later AppendEntries messages and apply committed entries in log order.

Raft maintains the Log Matching Property: if two logs contain an entry with the same index and term, the logs are identical in all entries up to that index. AppendEntries enforces this with a consistency check: the leader includes the index and term of the entry that immediately precedes the new ones, and the follower refuses the new entries if it does not have that entry. When a check fails, the leader decrements nextIndex for that follower and retries until the logs agree, then overwrites the follower's conflicting entries.

Safety

Raft adds an election restriction so that a new leader always holds every committed entry. A server denies its vote if its own log is more up-to-date than the candidate's log. Logs are compared by the term of their last entry first, and by log length if the last terms are equal.

A leader never commits entries from previous terms by counting replicas alone. It only commits an entry from its current term by counting replicas; earlier entries then become committed indirectly through the Log Matching Property.

Cluster membership changes and snapshots

Adding or removing servers safely is tricky because switching every server at once could create two independent majorities. The original paper uses joint consensus, an intermediate configuration in which decisions require separate majorities of both the old and the new configuration. Many implementations instead change membership one server at a time.

Logs cannot grow forever. Each server independently takes a snapshot of its state machine, records the last included index and term, and discards the log entries the snapshot covers. A leader sends an InstallSnapshot message to a follower that has fallen so far behind that the entries it needs were already discarded.

Where Raft is used

Raft is used in production by etcd, the key-value store that holds all Kubernetes cluster state, as well as by Consul, CockroachDB and TiKV.
